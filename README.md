> An adversarial test suite that attacks LLM applications, maps every attack to the
> OWASP LLM Top 10, adds a guardrails layer, and quantifies the reduction in attack
> success rate — with a measured false-positive rate on benign traffic and
> auditable PDF security reports.

**Demo (static gallery of 50 executed attacks):** [`demo/index.html`](demo/index.html) ·
**Results:** [`eval/RESULTS.md`](eval/RESULTS.md) · **Reports:** [`eval/reports/`](eval/reports)

## What this project does

Security teams shipping LLM features need to know, concretely, how their assistant
behaves under attack. This framework fires a corpus of 106 hand-labelled attacks
(plus HarmBench and JailbreakBench) at a running LLM system, decides for each one
whether the system was compromised, and reports attack success per OWASP category
— before and after a guardrails layer, alongside how often those guardrails
wrongly block legitimate users.

## Industrial use case

AI Safety Engineer / MLSec roles at Robust Intelligence, Lakera, Protect AI and
HiddenLayer, and any regulated buyer (banking, insurance, healthcare, government,
defense) that must show an auditable LLM security posture. The PDF report and the
reproducible OWASP table are the artifacts a compliance review asks for.

## Architecture

![Architecture](docs/architecture.svg)

The corpus feeds an async runner that sends each attack to a target through a
per-system adapter, sanitises and analyses the response, maps it to an OWASP
category, and aggregates baseline-vs-guardrailed success plus the false-positive
rate. See [`docs/architecture.md`](docs/architecture.md).

## Métricas y resultados

From [`eval/RESULTS.md`](eval/RESULTS.md), regenerated by `python -m eval.run`.
Three scenarios are saved in `eval/runs/`.

### Synthetic target (framework demonstration)

A deliberately-vulnerable in-repo assistant proves the corpus, analyzer and
guardrails end to end:

| Metric | Value |
|---|---|
| Attack success (baseline) | **26.4%** (28/106) |
| Attack success (with guardrails) | **5.7%** (6/106) |
| Absolute reduction | **20.8 pp** |
| Guardrail false-positive rate | **0.0%** (100 benign queries) |
| Mean guardrail latency | < 1 ms |

### Real targets — Project 01 and Project 03 (deterministic fallback, no LLM)

Both systems were started locally and scanned over HTTP. **They had no LLM
configured** (`llm_enabled=false`), so they answered with their deterministic
fallback — there is no model to jailbreak. Attack success was **0.0%** for both:
Project 01 ignores injections and returns product matches; Project 03 rejects
most payloads at input validation (HTTP 422, a defensive refusal). This measures
the framework and the guardrail path, **not** the targets' quality under a real
model. The run against a real LLM is `pendiente (requiere ANTHROPIC_API_KEY)`.

Mandatory table (per OWASP category, baseline vs guardrails vs FP rate) for every
scenario is in [`eval/RESULTS.md`](eval/RESULTS.md). Security reports are in
[`eval/reports/`](eval/reports) (`security-report-p01-chat.pdf`,
`security-report-p03-research.pdf`).

## Quickstart

```bash
make install                      # venv + pip install -e ".[dev]"
make test                         # pytest, coverage ≥ 70% (currently 97%)
make eval                         # synthetic scenario -> eval/RESULTS.md

# scan a live target (start Project 01 first: uvicorn src.api.main:app --port 8001)
make eval-p01                     # real run against Project 01 (chat adapter)
python -m ai_safety_framework.cli scan --url http://localhost:8001 --adapter chat

# serve the API
uvicorn ai_safety_framework.api.main:app --port 8000
curl -s localhost:8000/health

# regenerate the demo gallery and the PDF reports
python scripts/bake_demo.py
make report
```

Download the external corpora (HarmBench + JailbreakBench) and refresh the
manifest with `make data` (writes `data/MANIFEST.txt` and `data/licenses/`).

## Attack corpus

- **106 own attacks**, all ten OWASP LLM categories, hand-written ground truth
  (`success_indicators`, `expected`, `severity`). Techniques include direct/indirect
  injection, base64/ROT13/unicode/leetspeak obfuscation, XSS and unsafe-output
  handling, memory/knowledge-base poisoning, DoS probes, supply-chain payloads,
  PII/secret fishing, insecure tool use, excessive agency, overreliance and model
  theft.
- **100 legitimate queries** (15 tricky) for the false-positive rate.
- **HarmBench (400)** and **JailbreakBench (100)** downloaded by
  `scripts/download_data.py`, both MIT, hashed in `data/MANIFEST.txt`.

## Technical decisions

1. **ML detectors behind a `Protocol` with lazy imports** — the base install stays
   light; torch/transformers/presidio live in the `ml` extra and are mocked in tests.
2. **Rule-based success first, LLM-judge second** — deterministic and reproducible
   in CI; the numbered-rubric judge is layered on and gated on a key.
3. **`HttpTarget` + adapters** — one client, a tiny adapter per system; retries only
   5xx/network, treats 4xx as a defensive rejection.
4. **Model pinned to `claude-sonnet-4-5-20250929`** with timeouts and tenacity.
5. **Deterministic fallback labelled everywhere** — no fabricated metrics; numbers
   come only from a saved `eval/runs/*.json`.
6. **SQLite by default, Postgres behind the same interface.**

Full rationale in [`docs/decisions.md`](docs/decisions.md).

## Known limitations

- The offline runs use targets with **no LLM**; the real-LLM run needs
  `ANTHROPIC_API_KEY` and is marked pending.
- Refusal detection is phrase-based and success indicators are literal substrings,
  so the reported success rate is a **lower bound** (the LLM judge mitigates this).
- The corpus is single-turn; multi-turn attacks are future work.
- ML detectors are implemented and unit-tested with mocks but not run here (Hugging
  Face is blocked in this environment).
- `docker-compose` is written but not validated (no Docker daemon here).

See [`docs/error_analysis.md`](docs/error_analysis.md).
